# 취향 고리. 골드 사례와 점검

사용자가 결과물에 하는 모든 수정은 정보입니다. 저장하면 같은 수정을 두 번 할 필요가 없습니다. 파일 둘, 둘 다 활성 브랜드 폴더.

```
./brand/
  checks.md               <- 사용자의 수정에서 온 예/아니오 점검 (덧붙이기만, 어느 스킬이든)
  gold/<skill>/           <- 골드 사례마다 파일 하나. 쓴 것, 나간 것, 이유
```

로더가 실행 중인 스킬에 태그된 점검 (`all` 포함)과 그 스킬의 최신 골드 사례 셋을, `preferences.md`를 찍는 것과 같은 방식으로 찍습니다. 결과 데이터는 여전히 /performance-review를 통해 `learnings.md`로 갑니다. 취향 고리는 사장님이 승인하는 것을, 결과 고리는 시장이 승인하는 것을 기록합니다.

## 넘기기 전에

1. 맥락 블록이 이 스킬의 골드 사례를 나열하고, 같은 종류의 글을 쓰면, 최신을 먼저 읽습니다. 그것이 기준입니다.
2. 불러 온 모든 점검에 초안을 예 또는 아니오로 답합니다. 모든 답이 예가 될 때까지 다시 씁니다. 조용히. 목록이나 점수를 보여 주지 않습니다.
3. 점검이 오늘 사용자가 청한 것과 충돌하면, 오늘 요청이 이깁니다. 출처와 가정에 한 줄.
4. 점검이 돌았으면, 출처와 가정이 한 줄로 말할 수 있습니다 ("저장한 점검 9개와 대조했습니다."). 그 이상 없습니다.

## 사용자가 결과물을 고치면

신호.

- 고친 버전을 붙여 넣거나 설명합니다.
- 한 줄을 다시 쓰고 그것을 쓰라고 합니다.
- 이유를 들어 거절합니다 ("영업 냄새가 나요", "우리는 그렇게 말 안 해요").
- 한 편을 기준으로 표시합니다 ("이게 그거예요", "이게 기준이에요").

그다음.

1. 수정을 먼저 적용합니다. 일이 장부보다 앞입니다.
2. 골드 사례를 `./brand/gold/<skill>/<YYYY-MM-DD>-<slug>.md`에, 아래 템플릿으로 저장합니다. 이유는 사용자의 말을 인용합니다.
3. 서로 다른 수정마다 점검 하나, 대개 하나에서 셋, `./brand/checks.md`에 덧붙입니다.
4. 한 줄로 확인합니다. 새 점검을 부릅니다. "골드 사례로 저장했습니다. 새 점검. 헤드라인이 고객의 말을 쓰나요? 모든 숫자가 브리프와 맞나요? 하나를 빼려면 그 점검을 빼 달라고 말하세요."

저장하지 않는 것.

- 이 편에만 해당하는 사실 (이번 주 행사 날짜).
- 규칙으로 말한 상시 규칙 ("싼이라는 말은 절대 쓰지 마"). /start-here를 통해 `preferences.md`로 갑니다.
- 사용자가 한 번이라고 부른 수정.

브랜드 폴더가 아직 없나요? `./brand/`를 이 파일들만으로 만듭니다. 다른 것은 필요 없습니다.

## 좋은 점검을 쓰는 법

- **예가 좋음입니다.** "첫머리가 상품보다 먼저 문제를 부르나요?"
- **점검마다 생각 하나.** "짧고 구체적"은 둘로 나눕니다.
- **일만 읽고 확인할 수 있고,** 두 사람이 같은 답을 낼 만큼 구체적. "펀치가 있나?"는 이 시험에 실패합니다. "모든 문장이 20단어 미만인가?"는 통과합니다. 한국어면 "모든 문장이 두 줄을 넘지 않나?"처럼, 일만 보고 갈리는 기준.
- **다음에 적용될 만큼 일반적.** 수정이 대표하는 규칙. 수정 자체는 아닙니다 ("문제의 고객 말을 쓰나?"이지, "온수가 없다고 쓰나?"가 아닙니다).
- **실제 수정에서만.** 사용자가 주지 않은 점검을 지어내지 않습니다.
- **태그.** 스킬, 또는 수정이 사업이나 말투에 관한 것이면 `all` (사실, 절대 안 쓰는 말, 가격을 말하는 방식).
- **중복 없음.** 덧붙이기 전에 거의 같은 것을 찾습니다. 있으면 그 점검을 날카롭게 하고, 또 하나를 더하지 않습니다.

형식, 한 줄씩.

```markdown
# Checks

- [all] 모든 숫자와 제목이 브리프와 정확히 맞나요? (2026-11-16, gold/positioning-angles/2026-11-16-homepage.md)
- [direct-response-copy] 헤드라인이 문제를 고객의 말로 부르나요? (2026-11-16, gold/direct-response-copy/2026-11-16-boiler-page.md)
```

한 스킬의 점검이 30개를 넘으면, 거의 같은 것을 가장 날카로운 하나로 합칩니다. 은퇴한 점검은 `./brand/.history/checks.<YYYY-MM-DD>.md`로 옮깁니다. 지우지 않습니다.

## 골드 사례 템플릿

```markdown
# <짧은 이름>

- Skill: direct-response-copy
- Date: 2026-11-16
- Request: "<청한 것, 그들 말로>"

## What I wrote
<바뀐 부분만, 원문>

## What shipped
<그 부분의 최종, 원문>

## Why
> "<그들 말>"

## Checks added
- [direct-response-copy] 헤드라인이 문제를 고객의 말로 부르나요?
```

## 점검을 관리

"점검 보여 줘"는 스킬별로 묶어서 나열합니다. "그 점검 빼" 또는 "X에 대한 점검 빼"는 `.history`로 옮깁니다. "왜 맨날 X를 해?"는 그 스킬의 점검과 골드를 읽고, 원인인 하나의 이름을 말합니다. 이 요청은 /start-here로 보냅니다.
