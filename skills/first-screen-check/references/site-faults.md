# 신뢰를 깎는 오류

**4단계를 돌릴 때 불러옵니다.** 페이지 소스, 리다이렉트, 사이트 구조에 있습니다. 손님이 직접 보는 일은 드물지만, 순위, 나쁜 데이터를 반복하는 AI 답변, 실제 가격·별점과 달라 속았다는 느낌을 통해 전화를 깎습니다. 아래 형태는 일반적인 설명입니다. 앞에 있는 사이트와 대조합니다.

## 지어내거나 낡은 가격

**확인:** 페이지와 구조화 데이터의 가격 문자열을 전부 읽습니다. 스크립트는 JSON-LD `priceRange`와 `$` 또는 "원"이 들어간 FAQ 답을 출력합니다. 사장님에게 하나만 묻습니다. "이게 실제로 받는 금액인가요?"

**흔한 형태:** FAQ 구조화 데이터에 사장님이 한 번도 받지 않은 범위가 있습니다. 사이트를 만든 사람이 넣었습니다. AI 답변과 검색 스니펫은 FAQ를 그대로 가져가므로 틀린 가격이 페이지보다 멀리 갑니다.

**고침:** 실제 방식을 말로 적습니다. "현장 보고 작업 전에 글로 견적". 숫자를 공개하지 않으면 범위를 지어내지 말고 견적이 어떻게 나오는지만 적습니다. 보이는 FAQ와 구조화 데이터가 같은 말을 하게 합니다. 거짓·과장은 표시광고법에서 금지됩니다.

## 박아 넣은 리뷰 데이터

**확인:** 구조화 데이터의 `aggregateRating`을 지금 네이버 플레이스와 비교합니다. 구글 비즈니스 프로필이 있으면 그것도 비교합니다. 스크립트가 출력한 `address`가 실제 영업 지역과 같은지 봅니다.

**흔한 형태:** 구조화 데이터에 완벽한 5.0이 박혀 있고, 플레이스가 바뀌어도 그대로입니다.

**왜 중요한가:** 구글은 2019년부터 업체가 자기 리뷰를 별점으로 보여 주지 않습니다. 리뷰 스니펫 가이드는 리뷰 대상이 그 리뷰를 통제하는 페이지를 `LocalBusiness`나 `Organization` 마크업의 별점 결과에서 빼며, 구글·페이스북 리뷰 위젯을 심은 경우도 포함합니다. 박아 넣은 점수는 검색에서 득이 없고, 플레이스와 어긋난 숫자는 손님이 확인할 수 있는 주장입니다. 네이버는 이 구글 규칙과 별개로, 페이지 별점과 플레이스 별점이 다르면 손님이 바로 비교합니다.

**고침:** 구조화 데이터에서 고정 별점을 뺍니다. 실제 주소나 서비스 지역이 있는 `LocalBusiness`(또는 `Plumber` 같은 업종 하위 타입) 하나만 둡니다. 사람에게 보여 줄 별점은 페이지 글자로, 전화 버튼 근처에, 지금 플레이스 값으로 둡니다.

## 오류 페이지로 끝나는 리다이렉트

**확인:** 사이트로 사람을 보내는 URL을 모읍니다. 플레이스 웹사이트, 각 광고의 최종 URL, 디렉터리 링크, 사이트맵이나 크롤의 옛 URL. 하나씩 따라갑니다.

```bash
curl -sIL -A "Mozilla/5.0 (iPhone)" <url> | grep -iE "^HTTP|^location"
```

마지막 상태는 200이어야 합니다. 스크립트는 URL 하나에 같은 홉을 출력합니다.

**흔한 형태:** 예전 사이트 주소가 404로 바로 리다이렉트됩니다.

**왜 중요한가:** 광고나 플레이스 링크가 오류 페이지에 닿으면 그 클릭은 전부 낭비이고, 다른 사이트의 죽은 링크는 더 이상 세지지 않습니다.

**고침:** 옛 URL마다 리다이렉트 하나로 가장 가까운 살아 있는 페이지를 가리킵니다. 배포 뒤 curl을 다시 돌립니다. 슬래시와 www 규칙이 겹치는 일이 많습니다.

## 무거운 이미지

**확인:** 스크립트의 첫 이미지 목록(용량은 서버 또는 다운로드) 또는 PageSpeed Insights의 이미지 크기·차세대 형식 항목.

**흔한 형태:** 홈 히어로가 수 MB 데스크톱 사진이고, 모든 휴대폰에 그대로 갑니다.

**고침:** 히어로는 휴대폰 크기 WebP나 AVIF를 보내고, 데스크톱 폭에서만 큰 버전을 보냅니다. 대부분의 사이트 빌더에서는 재구축이 아니라 설정이나 플러그인입니다.

## 동·구만 바꾼 페이지

**확인:** 상권 페이지 두세 개를 가져와 지역명을 빼고 비교합니다.

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/page_facts.py <town-page-1> --compare <town-page-2> --compare <town-page-3> --town 수성구 --town 달서구 --town 중구
```

먼저 템플릿 바닥을 구합니다. 상권 페이지와, 고유하다고 아는 서비스 페이지를 비교합니다. 공통 메뉴, 푸터, 행동 유도 때문에 한 사이트의 두 페이지는 어느 정도 같습니다. 그 바닥보다 훨씬 높고 시·군·구·동만 바뀐 페이지는 복붙입니다. 비교 대상이 다른 페이지로 리다이렉트되면 독립 페이지가 아니고, 스크립트가 그렇게 말합니다. 예시 지역은 대구의 구입니다.

**흔한 형태:** 같은 글에 구 이름만 바꾼 상권 페이지 묶음.

**왜 중요한가:** 검색은 거의 같은 글을 한 페이지로 보고 무엇을 노출할지 고릅니다. 착지한 손님은 자기 동에 대해 새로 아는 것이 없습니다. 고침은 더 적고 나은 상권 페이지(실제 작업, 이동 시간, 가는 동네)이거나, 얇은 동을 서비스 지역 페이지 하나로 접는 것입니다. `/service-area-pages`와 `/local-seo-plan`이 방법을 다룹니다.

## 번호가 서로 다름

**확인:** 사이트의 모든 번호(스크립트가 본문과 구조화 데이터 `telephone`의 서로 다른 번호를 출력), 플레이스(서비스 설명과 소식 포함), 디렉터리 등록을 나열합니다. 각각은 가게가 받고 추적하는 회선이어야 합니다.

**흔한 형태:** 플레이스나 디렉터리 구석에 남은 옛 번호가 콜트래킹 밖의 회선으로 전화를 보내, 어떤 보고서에도 안 잡힙니다.

**고침:** 손님이 읽는 곳마다 대표 번호 하나. 추적 번호는 추적 도구가 바꿔 넣는 곳에서만. 분기마다 플레이스 텍스트 필드를 봅니다. 잊기 쉽습니다.

## 오류를 같이 읽기

오류 하나는 수정입니다. 여러 개가 같이 있으면(거짓 가격, 고정 별점, 복붙 상권 페이지) 보통 사장님에게 묻지 않고 템플릿으로 만든 사이트입니다. 보고서에 있는 그대로 말합니다. 가장 싼 고침은 패치 목록이 아니라 사이트 전체를 한 번 정직하게 보는 것일 수 있습니다.
