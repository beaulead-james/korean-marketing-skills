# 통화 기록 조리법. 손, 스크립트, API

스크립트가 내보내기를 못 읽거나, 스프레드시트로 분석하거나, 전화 시스템 API에서 통화와 문자를 당길 때 읽어요. 직접이든 연결 도구를 통하든. API 세부는 움직이고, 아래 함정은 날짜가 있어요. 한국 기본은 통신사 인터넷전화, 대표번호, 네이버 스마트콜, 카카오 채널, 상담 도구예요. Quo 같은 해외 API는 그 도구를 쓸 때만.

## 필요한 필드

통화마다. 시작 시각, 방향(수신 또는 발신), 상태(받음, 부재중, 음성사서함), 통화 시간, 고객 번호, 사업자 회선. 메시지마다. 시각, 방향, 고객 번호. 열 이름은 시스템마다 다르고, 스크립트는 고른 열을 인쇄해요. 덮어쓰기 플래그는 `--time-col`, `--direction-col`, `--status-col`, `--duration-col`, `--from-col`, `--to-col`, `--party-col`, `--line-col`.

어떤 내보내기든 볼 것.

- **시간대.** API 내보내기는 종종 UTC. 영업시간으로 나누기 전에 한국 시간으로. 타임존이 붙은 시각만 `--utc-offset 9`. 썸머타임은 없어요. 이미 한국 시각인 파일은 다시 밀지 않아요.
- **부재중과 음성사서함.** 어떤 시스템은 음성사서함을 녹음 있는 부재중으로, 어떤 시스템은 시간이 있는 받음으로 남겨요. 아는 통화 다섯 줄과 손으로 맞춰요. 스크립트는 상태 칸의 영어(missed, voicemail, answered)를 봐요. "부재중", "음성사서함"은 그 단어에 안 걸리면 통화 시간으로만 나뉘어요.
- **돌려주기와 링그룹**은 고객 통화 하나를 여러 행으로 남겨요. 고객 번호와 시작 시각 1분 안으로 합쳐요.
- **고객 번호**는 수신의 "보낸 사람", 발신의 "받는 사람"이에요.
- **방향 한글.** "수신/발신"은 스크립트가 인바운드로 못 봐요. `inbound` / `outbound`로 바꾼 뒤에 돌려요.
- **시각 형식.** `YYYY-MM-DD HH:MM:SS`가 맞아요. `2026.11.18`이나 "오전/오후"는 읽기 전에 바꾸세요.
- **번호 키.** 스크립트는 숫자만 남기고 끝 10자리예요. `01012345678`과 `821012345678`은 같은 키. 서울 02는 어긋날 수 있으니 다섯 줄을 봐요.

## 스프레드시트로 손 계산

1. 열을 더해요. `date`(날짜), `hour`, `weekday`, `in_hours`(평일이고 시간이 영업시간 안이면 TRUE), `real`(받았고 30초 이상).
2. 수신을 `in_hours`와 상태로 피벗해 수신율.
3. 부재중 수신을 `weekday`와 `hour`로 피벗해 히트맵.
4. 후속 시간. 고객 번호, 그다음 시각으로 정렬. 부재중 수신마다, 같은 번호로 간 다음 발신 전화·문자·알림톡·카카오 답이 후속. 시각을 빼요. 고객이 나중에 걸어 받은 통화는 "닿음"이지 빠른 후속이 아니에요.
5. 못 닿은 발신. 부재중이 있고 24시간 안에 나가는 연락도, 받은 통화도 없는 번호.

## 발신자가 묻는 것 (선택. 시스템에 요약이나 녹취가 있을 때)

요약에서 요청을 라벨해요. 문제, 잡힌 일의 상태 확인, 가격 질문, 지역 밖, 안 하는 서비스. 에이전트가 초안을 잡을 수 있고, 믿기 전에 표본을 손으로 봐요. 한 달 분석에서 손으로 본 라벨이 맞았던 적이 있어요. 특정 업체의 정확도 주장이 아니에요. 라벨은 어떤 전화를 광고가 데려오는지, 어떤 전화는 웹사이트가 답해야 하는지(지역, 가격, 영업시간), 문자로 막을 상태 확인이 몇 건인지 보여요.

## API 함정 (Quo, Composio 경유, 2026년 9월에 본 것)

이 도구를 쓰는 계정에만 해당해요. 한국 기본 경로가 아니에요.

- Composio Quo 도구 모음에 통화 요약·녹취 도구가 없었어요. Quo 자신의 API로 프록시가 됐어요. `https://api.quo.com/v1/call-summaries/{callId}`와 `/v1/call-transcripts/{callId}`. 옛 `api.openphone.com` 호스트는 프록시가 거절했어요.
- 통화 목록은 참가자 **하나**(항목 하나짜리 배열)와 전화번호 ID가 필요했어요. 모든 통화를 당기려면 고객 번호를 순회해요. 메시지 목록은 `participants`였어요. 모양이 틀리면 실행 안에서 예외로 검증이 실패하고, 깨끗한 오류가 아니에요.
- **대화 `updated_after`는 과다 집계.** 상태 변경(대화를 완료로 표시하는 것)도 대화를 갱신해서, 옛 대화가 새 활동으로 돌아와요. 마지막 활동 시각으로 거르세요.
- 원시 기록을 먼저 워크스페이스 파일로 받고 그다음 분석. 질문마다 다시 당기면 느리고 호출 한도에 닿아요.

## 세면 안 되는 통화

- **커버가 얇은 자동 분류.** 한 기록에서 분류기가 한 달 통화를 전부 "불확실"로 둔 적이 있어요. 자동 라벨을 건수로 쓰기 전에 커버를 봐요.
- **30초 필터 없는 원시 수신.** 스팸과 잘못 걸림이 짧은 통화의 큰 몫일 수 있어요.
- **모든 회선의 통화.** 기사 개인 회선이나 거래처 회선이 수신율을 왜곡해요. 손님이 거는 회선만 `--line`으로.

## 개인정보

기록은 고객 데이터예요. 내보내기와 못 닿은 목록은 워크스페이스에 두고 버전 관리 밖에 둬요 (`.gitignore`). 일이 끝나면 작업 복사본을 지워요. 보고서에는 건수와 비율만. 번호와 이름은 없어요.
